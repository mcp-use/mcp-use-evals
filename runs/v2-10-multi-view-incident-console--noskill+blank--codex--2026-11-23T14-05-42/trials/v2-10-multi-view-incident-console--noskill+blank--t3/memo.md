The decisive wrong turn was entry placement: the agent created root-level `index.ts` and `server.ts`, with `index.ts` containing `export { default } from "./server.js";`, rather than placing an entry under `src/`. This was reinforced by the package README it consulted, which said, `Replace its index.ts with a view-bound tool like this:`; the local CLI then confirmed the misleading layout with `[mcp-use] built index.ts + views ... → .mcp-use/build/index.js`. Thus its local build/start verification did not expose the evaluator’s expected entry convention.

Discovery was node_modules-driven and somewhat meandering. The agent first searched broad API terms via `rg -n "createMcp|defineTool|registerTool|registerApp|App" node_modules/mcp-use`, then inspected several declaration files, and later relied on `node_modules/mcp-use/README.md` for the view convention. One search also hit a documentation gap directly: `rg: node_modules/mcp-use/docs: No such file or directory`.

Typed React integration caused a failed typecheck before the agent discovered the required module augmentation. The initial errors were `Property 'incident' does not exist on type 'unknown'` and `'context.toolOutput' is of type 'unknown'`; it then grepped for `mcp-env|RegisteredTools|declare module` and created `mcp-env.d.ts` with `interface Register { tools: typeof server; }`. This requirement was discoverable only through SDK declarations stating `Augmented by the project's mcp-env.d.ts; empty by default.`, making it a notable setup papercut.

The final verification was thorough but gave false confidence about packaging compatibility: the agent reported `npx mcp-use build --inline succeeds` and `PORT=3210 npx mcp-use start served MCP at /mcp`, while all of that exercised the root `index.ts` layout. A final cleanup/check command also produced unrelated noise, `fatal: not a git repository`, because it ran `git status --short` in the blank workspace.
