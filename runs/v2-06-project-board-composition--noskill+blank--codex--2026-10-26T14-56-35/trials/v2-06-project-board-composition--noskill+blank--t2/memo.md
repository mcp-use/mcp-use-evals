The main time sink was API discovery: after `npm view mcp-use readme --json` returned no README content, the agent inspected the installed package directly with `sed -n '1,240p' node_modules/mcp-use/README.md`, then queried declarations via `sed -n '1,280p' node_modules/mcp-use/dist/server.d.ts` and repeatedly grepped for `listen(` and `resourceTemplate`. This indicates the npm metadata alone did not provide enough usable guidance for the resource-template and listener APIs.

Verification was more repetitive than necessary. The agent first ran a lifecycle that produced `empty board: Open issues: 0` through `missing resource: Issue 999 not found`, then explicitly announced “`one final clean-server lifecycle run`” and repeated the same sequence on port 3101. It also performed separate manual initialization and resource-list checks, including `resources: board://summary` and `templates: issue://{id}`, rather than using one consolidated client run.

A generic repository check caused avoidable noise because the blank workspace was not a Git repository: `git diff --check` returned `warning: Not a git repository` followed by the full Git usage text. Process shutdowns likewise appeared as failed tool results despite successful testing: both server sessions ended with `exitCode":143` and `"status":"failed"` after explicit `kill` commands, which could confuse automation or an agent interpreting tool status.

Dependency installation surfaced ecosystem papercuts: npm reported `5 vulnerabilities (3 low, 2 high)` initially and warned that `esbuild@0.28.2` had “`install scripts not yet covered by allowScripts`.” After package modification and reinstall, it still reported `4 vulnerabilities (3 low, 1 high)`, although neither warning blocked the implementation.
