The main discovery friction was obtaining the SDK API shape. The first README attempt failed with `SyntaxError: /tmp/mcp-use-readme.json: Unexpected end of JSON input`, so the agent switched to `npm pack mcp-use --pack-destination /tmp`, extracted the package, and inspected `README.md`, `dist/server.d.ts`, and `dist/resources.d.ts`. It then grepped declarations for `"listen\\(|resourceTemplate|resources/list|resource\\("`, relying on the packaged README and type files rather than a fetched docs page.

The initial scaffold caused two TypeScript issues: `Cannot find name 'process'` and `The current file is a CommonJS module and cannot use 'await' at the top level.` Installing `@types/node` alone did not resolve the former—the next check still reported `Cannot find name 'process'`—and required a separate `tsconfig.json` modification. The CommonJS mismatch originated in npm’s generated package metadata, which initially contained `"type": "commonjs"`.

Verification had avoidable CLI and process-management detours. Trying `npx mcp-use client docs resources templates list` produced only `Usage: mcp-use client docs <tools|resources|prompts|auth> ...`, and `npx mcp-use client docs resources --help` showed that resources support only `list` and `read <uri>`. Running `git diff --check` in the blank workspace also failed noisily with `warning: Not a git repository.`

The first cleanup targeted the wrong process: after `kill 556`, the subsequent process check still showed `node node_modules/.bin/tsx src/server.ts` with PID 597, requiring another explicit `kill 597`. Despite these papercuts, the live MCP client exercise successfully issued `resources/read docs://index`, `resources/read docs://getting-started`, `resources/read docs://unknown`, and two `tools/call search_docs` requests, each logged with `/mcp 200`.
