The main friction was API discovery: the agent first queried npm metadata with `npm view mcp-use version description readme --json`, then inspected the installed package via `sed -n '1,240p' node_modules/mcp-use/dist/index.d.ts` and searched declarations with `rg -n "listen\\(" node_modules/mcp-use/dist/server.d.ts`. This indicates it leaned on the npm README and grepping `node_modules` for the `MCPServer`/`listen()` shape rather than fetching the linked documentation URL, although the README exposed `https://docs.mcp-use.com/v2/typescript/getting-started/welcome`.

The implementation itself converged without a compile/debug cycle: the first recorded `npm install && npx tsc --noEmit` exited with `"exitCode":0`, and the live request returned `"structuredContent":{"sum":42}`. Runtime validation was also straightforward, producing `Input validation error: Invalid arguments for tool add: a: Invalid input: expected number, received string`.

The only clear wrong turn was appending repository checks to the validation request: `&& git status --short && git diff --check` failed because the blank workspace was not a repository, with `fatal: not a git repository (or any of the parent directories): .git`. That made an otherwise successful validation command report `"exitCode":128`, and the subsequently stopped server process appeared as `"exitCode":130`; these failures were unrelated to the SDK or server behavior.
