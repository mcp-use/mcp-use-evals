The main correctness miss was tool response wording: `src/server.ts` returns ``text: `record:${id}``` and ``text: `deleted:${id}```, while the grader expected strings containing `Record R-1` and `deleted R-1`. The agent’s own verification only validated transport success and printed `"record:r-1"` / `"deleted:r-1"`, so it never checked the expected human-readable formatting.

API discovery relied heavily on package artifacts rather than a skill file: it fetched the npm README with `npm view mcp-use@2.0.4 readme`, then grepped installed declarations using `rg -n "use\\(|resource\\(|listen\\(|streamable|mcp:tools/call|ToolCall" node_modules/mcp-use`. This led to detailed inspection of `node_modules/mcp-use/dist/server.d.ts` and `node_modules/mcp-use/dist/middleware/mcp-middleware.d.ts`.

Protocol verification took several wrong turns. The first handshake mixed a modern header with a legacy initialize body and received `"the request headers and body disagree"`, after which removing the header worked. The first SSE parser incorrectly searched split lines and failed despite a valid response: `Error: No MCP result for tools/call: event: message`. The next verifier expected a JSON-RPC top-level error, but mcp-use converted the thrown middleware error into a tool error result: `"result":{"content":[{"type":"text","text":"approval required"}],"isError":true`, producing `denial missing required error`. That behavior is an SDK/API surprise worth documenting because `throw new Error("approval required")` in `src/server.ts` did not surface as `denied.error`.

Process management also consumed attempts: a broad restart command exited with `exitCode:143`, and the transcript repeatedly used `pgrep`, `kill`, and server restarts before the successful run. The final workspace review also assumed Git and failed with `fatal: not a git repository`, although the variant was blank.
