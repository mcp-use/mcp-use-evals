The main discovery cost was working out the SDK shape from the installed package rather than a concise external example: the agent searched declarations with `rg -n "Streamable|streamable|createMCP|McpServer|tool\\(" node_modules/mcp-use` and then read `node_modules/mcp-use/README.md`, `dist/server.d.ts`, `dist/tools.d.ts`, and `dist/config.d.ts`. The initial `npm view mcp-use readme --json` produced no README content, after which the agent moved to those local files.

Dependency compatibility caused an avoidable reinstall. The agent first ran `npm install mcp-use@2.12.2 zod@3.24.2`, then discovered the SDK bundled Zod `4.6.7` while the project had `3.24.2`, and corrected this with `npm install zod@4.6.7`. This suggests the SDK’s expected Zod major was not obvious up front.

The first typecheck failed despite `@types/node` being installed: `error TS2591: Cannot find name 'process'. Do you need to install type definitions for node? ... add 'node' to the types field in your tsconfig.` The subsequent inspection showed `@types/node@26.6.6` present and a `tsconfig.json` without a `types` entry; the agent then modified the config and reran successfully. That error was straightforward but added a diagnostic round trip.

Verification was thorough but manually verbose: the lifecycle used separate raw `curl` JSON-RPC commands for initialization and every tool call, each repeating headers such as `Accept: application/json, text/event-stream` and `MCP-Protocol-Version: 2025-11-25`. The final hygiene command also assumed Git metadata that the blank workspace lacked, ending with `fatal: not a git repository (or any of the parent directories): .git`; because it chained `npx tsc --noEmit && git status`, the typecheck completed before that unrelated failure.
