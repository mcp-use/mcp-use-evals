The decisive wrong turn was placing the entry at repository root: the agent created `index.ts`, while the deterministic check only tried `src/server.ts` and `src/index.ts` (`entry: FAIL — no entry file found (tried: src/server.ts, src/index.ts)`). This was reinforced by the installed SDK documentation, which said `Replace its index.ts with a view-bound tool like this`, and by the CLI successfully reporting `[mcp-use] built index.ts + views ... → .mcp-use/build/index.js`; the mismatch between CLI-supported layout and grader-required layout was therefore easy to miss.

The agent spent substantial discovery effort inspecting package internals rather than using a scaffold: it ran `npm view mcp-use@2.0.4 readme`, searched `node_modules/mcp-use/dist`, opened `node_modules/mcp-use/README.md`, and grepped the bundled CLI for `"mcp-env|tsconfig|entry|views"`. That investigation did correctly uncover automatic view publication, summarized as `The installed framework’s view binding automatically publishes ui://views/<name>.html resources.`

Protocol verification had one avoidable failed attempt: the first initialize returned `400 Bad Request` because `an initialize request (legacy handshake) was sent with a modern MCP-Protocol-Version header`. Retrying without that conflicting header succeeded with `"protocolVersion":"2025-11-25"`.

The initial resource-marker script misleadingly reported `"resourceMarkers": {"list": false, "detail": false}` because it searched the generated HTML incorrectly; the agent then inspected the inline bundle and found snippets containing `{"data-view":\`incident-list\`` and `{"data-view":\`incident-detail\``. This illustrates that inline resources were very large—`length: 953052` and `length: 953218`—and source markers were transformed rather than preserved as literal HTML syntax.

The final verification command also produced a distracting failure solely from assuming Git metadata: `fatal: not a git repository (or any of the parent directories): .git`.
