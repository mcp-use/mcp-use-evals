The decisive wrong turn was placing the entry at repository root as `index.ts`, while the reported contract searched only `src/server.ts` and `src/index.ts`; the agent even confirmed the build target as ``built index.ts + views ... → .mcp-use/build/index.js`` but never moved it under `src/` or supplied a persistent entry configuration. The CLI exposed an escape hatch—``--entry <path> Server entry module``—but the agent did not use it in the final commands, which remained ``npx mcp-use build --inline`` and ``npx mcp-use start``.

Discovery relied heavily on npm and installed-package inspection: it fetched ``npm view mcp-use@2.0.4 readme --json`` and inspected declarations including ``node_modules/mcp-use/dist/server.d.ts`` and ``node_modules/mcp-use/dist/react/types/register.d.ts``. This did not prevent type-registration friction: the first typecheck failed with ``Property 'incident' does not exist on type '{}'`` and ``Property 'incidents' does not exist on type '{}'``. Running the build generated ``[mcp-use] created mcp-env.d.ts``, yet typechecking still failed until `tsconfig.json` was modified, indicating that generated registration was not initially included.

The scaffold/package editing introduced a duplicate module setting: the displayed `package.json` contained both ``"type": "module"`` and later ``"type": "commonjs"``. That produced the startup failure ``Cannot use import statement outside a module`` and required another package edit.

Client verification also hit an SDK/CLI papercut. `mcp-use client` announced ``installing @mcp-use/client…`` and npm reported success, but the command immediately said ``@mcp-use/client is not installed`` and instructed a manual install; the agent then ran ``npm install -D @mcp-use/client@2.0.0``.

The agent ultimately performed extensive wire checks—``tools/list``, ``resources/read``, and ``tools/call`` all returned 200 in the server log—but those checks validated the root-entry build rather than the grader’s required discoverable source entry.
