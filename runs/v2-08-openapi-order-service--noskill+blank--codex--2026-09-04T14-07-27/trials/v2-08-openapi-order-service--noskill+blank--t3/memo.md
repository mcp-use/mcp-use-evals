The agent relied heavily on installed package internals rather than external docs or a skill file, grepping `node_modules/mcp-use` for `"fromOpenAPI|Streamable|streamable"` and reading `node_modules/mcp-use/dist/server.d.ts` plus `openapi/types.d.ts` to discover `listen()` and OpenAPI API shapes.

There was one SDK export-path wrong turn: the first typecheck failed with `Cannot find module 'mcp-use/openapi' or its corresponding type declarations.` The agent then modified `src/server.ts`; the final source avoids that subpath by deriving the spec type from the public API: `type OpenAPIDocument = Parameters<typeof MCPServer.fromOpenAPI>[0]["spec"];` (`src/server.ts`).

The hand-written verifier initially assumed all tool results were successful. After the expected upstream 404, it failed at `Error: Expected a successful MCP tool result`, even though the SDK log already showed `tools/call getOrder ERROR order ord-1001 not found`. The verifier was then changed to inspect `isError` and text separately; final `src/verify.ts` checks `missing.result?.isError === true && resultText(missing.result).includes("not found")`. This exposes a small API surprise: upstream HTTP failures arrive inside a successful MCP HTTP exchange as an MCP tool error, not as a failed POST.

Some time was also lost to unrelated shell/process handling. A successful verification command was reported failed because it appended `git status --short` in a non-repository and received `fatal: not a git repository`; the next command confirmed the server processes were still running via `ps -ef | rg '[t]sx src/server.ts|[n]ode.*src/server'`, requiring `kill 414 447 458`. A later startup smoke test used `timeout 3s` and consequently returned `"exitCode":124` despite printing both listening URLs.
