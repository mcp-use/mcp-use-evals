The main miss was inconsistent decline wording. In `src/server.ts`, an explicit response action uses `return terminalError("Deployment was not approved.");`, while an accepted form with `approve: false` uses `return terminalError("Deployment was declined.");`. The live decline verification only exercised the former and printed `"text":"Deployment was not approved."`; the agent then concluded, `Verified decline prompts once, then returns a terminal isError result`, without checking that the response text contained “decline,” which caused the reported contract-call failure.

SDK discovery relied heavily on grepping installed declarations rather than a skill file or fetched docs: `rg -n "inputRequired|inputResponse|acceptedContent..." node_modules/mcp-use` and later searches under `node_modules/@modelcontextprotocol/server/dist`. The declarations did eventually expose useful examples such as ``acceptedContent<{ confirm: boolean }>(ctx.mcpReq.inputResponses, 'confirm')``, but locating them required several searches through bundled and hashed declaration files.

End-to-end testing encountered protocol papercuts. The first curl handshake failed with `406 Not Acceptable` and `"Client must accept both application/json and text/event-stream"`. After fixing the Accept header, the first tool call still failed because `"the client on this 2025-era connection did not declare the required capability"`, forcing the agent to inspect client declarations and construct a client pinned with `versionNegotiation: { mode: { pin: "2026-07-28" } }`. The first inline client attempt also failed because `Top-level await is currently not supported with the "cjs" output format`, requiring an async-IIFE retry.

Despite those detours, the manual initial-round check was useful and showed exactly one request: `"resultType":"input_required"` with `"deployment-approval"` and `"Approve production deployment?"`. The accepted-path test likewise returned `"structuredContent":{"environment":"production","deployed":true,"note":"Ship it"}`.
