The decisive miss was the read-tool response casing: `src/server.ts` returns ``text: `record ${id}```, while the grader expected `Record R-1`; the agent’s manual check actually displayed `"text":"record r-1"` but it still concluded, `"The end-to-end MCP exchange is working"`. Using lowercase test input (`"id":"r-1"`) rather than the grader-style `R-1` also made this contract mismatch easier to overlook.

API discovery depended heavily on installed-package inspection rather than external docs: the agent ran `rg ... node_modules/mcp-use`, read `node_modules/mcp-use/README.md`, and inspected files including `node_modules/mcp-use/dist/server.d.ts`, `tools.d.ts`, `resources.d.ts`, and middleware declarations. This involved some dead ends: `rg: node_modules/@mcp-use: No such file or directory` and a later inspection exited with code 2 because `node_modules/mcp-use/dist/server.js` and `middleware/mcp-middleware.js` were not at the assumed paths.

The initial dependency/schema setup was incompatible with the SDK’s schema requirement. TypeScript reported Zod objects were not assignable to `StandardSchemaWithJSON` because `"Property 'jsonSchema' is missing"`, and separately reported `Cannot find name 'process'`; the agent then modified `package.json`, reran `npm install`, and reached a passing typecheck. This suggests the SDK’s Zod-version/Standard Schema expectations were not obvious from the initial package metadata query (`npm view mcp-use@2.0.4 ... dependencies`).

The live protocol checks were otherwise useful and directly confirmed the middleware/resource behavior with `"approval required"` and `"1|read_record|allowed\n2|delete_record|denied\n3|delete_record|allowed"`.
