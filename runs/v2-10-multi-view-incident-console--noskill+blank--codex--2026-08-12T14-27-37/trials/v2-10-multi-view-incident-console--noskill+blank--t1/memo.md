The decisive mistake was entry-point placement: the agent created root-level `index.ts` (`[tool] fileChange({"event":"create","path":"index.ts"})`) rather than `src/server.ts` or `src/index.ts`, which left the grader unable to discover the server despite the local CLI reporting `built index.ts + views`. The agent had seen the CLI’s explicit override option, ``--entry <path> Server entry module``, but did not use it or align the layout with the expected conventional entry path.

The agent relied heavily on installed-package inspection rather than external docs or a skill file: it read `node_modules/mcp-use/README.md`, `node_modules/mcp-use/dist/server.d.ts`, `node_modules/mcp-use/dist/tools.d.ts`, `node_modules/mcp-use/dist/views/register.d.ts`, and later `node_modules/mcp-use/dist/react/hooks/use-tool-context.d.ts`. This did lead to functioning local tool/view bindings, evidenced by `Verified: 2 tools, 2 MCP App HTML resources, and matching per-tool view metadata.`, but did not expose the grader’s entry-discovery requirement.

A scaffold-editing papercut caused the first production start failure. The inspected `package.json` contained both `"type": "module"` and a later `"type": "commonjs"`, and start failed with `Cannot use import statement outside a module`. The agent then modified `package.json` and successfully started the server, so this was recoverable but consumed an extra debug cycle.

There was also a late type-registration regression after modifying both views. The next check failed with `Property 'incident' does not exist on type 'unknown'`, `Property 'incidents' does not exist on type 'unknown'`, and an implicitly-any callback. The agent responded by modifying `tsconfig.json`, after which `npx tsc --noEmit && npx mcp-use build --inline && npx tsc --noEmit` passed. This suggests the generated `mcp-env.d.ts` registration path—`tools: typeof import("./index.js");`—was sensitive to project configuration and created avoidable friction after an initially successful build.
