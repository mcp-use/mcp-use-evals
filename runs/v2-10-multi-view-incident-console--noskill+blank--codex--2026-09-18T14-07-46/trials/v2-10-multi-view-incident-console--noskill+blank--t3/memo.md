The decisive wrong turn was following the SDK scaffold’s root-entry convention rather than the evaluator’s expected `src/` convention. The scaffold explicitly reported `index.ts (server entry point)`, and the agent created only root `index.ts` (`index.ts`: `export default server;`); no `src/server.ts` or `src/index.ts` was produced. This explains why the agent’s own command succeeded—`[mcp-use] built index.ts + views`—while the deterministic result reports `entry: FAIL — no entry file found (tried: src/server.ts, src/index.ts)`.

Discovery consumed substantial effort. The npm README retrieval failed with `0 /tmp/mcp-use-readme.json` and `Unexpected end of JSON input`, after which the agent packed and inspected the package via `npm pack mcp-use@2.0.4`, `tar -tzf`, and extracted `package/README.md`, `package/dist/index.d.ts`, and other declaration files. It also fetched `https://mcp-use.com/prompt.md`, then inspected `create-mcp-use-app`. The first scaffold attempt failed because `Project name cannot contain path separators or ".."`; retrying from `/tmp` worked. No mcp-use skill file was used; the fetched prompt merely instructed `Install the mcp-use skill`, while the actual scaffold command included `--no-skills`.

Protocol verification had one avoidable false start: the first initialize returned `400 Bad Request` because `the request headers and body disagree`; removing the modern header and using body protocol `2025-11-25` then returned `HTTP/1.1 200 OK`. The agent nevertheless performed extensive successful live checks, including `tools/list`, `resources/list`, both resource reads, and both calls, reinforcing confidence in the root layout.

A final cleanup check also produced noise: `git status --short` failed with `fatal: not a git repository`, because it was chained after `npm ls --depth=0`; this did not reveal the missing `src/` entry.
