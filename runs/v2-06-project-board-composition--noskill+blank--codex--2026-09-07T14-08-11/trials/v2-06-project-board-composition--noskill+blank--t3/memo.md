The main time sink was SDK discovery: the agent first queried npm metadata (`npm view mcp-use version description repository.url --json`), then attempted to fetch the registry README (`npm view mcp-use readme --json`) but got no useful output, and finally inspected installed declarations such as `node_modules/mcp-use/dist/server.d.ts` and `node_modules/mcp-use/dist/resources.d.ts`. This node_modules inspection established the needed API shape, summarized as: `The SDK supports static resources and URI templates natively`.

Verification took a wrong turn because several hand-written curl payloads were malformed; the combined output repeatedly reported `Invalid JSON`. The agent diagnosed this as `an extra JSON brace`, stopped the server, restarted it to reset in-memory state, and reran the lifecycle with corrected requests. This manual JSON-RPC approach was brittle and added an entire server restart and verification pass.

The corrected combined curl command’s captured output only showed later lifecycle responses, beginning with `Issue 1 resolved`, rather than visibly showing the claimed empty-board and intermediate assignment reads. The server log did confirm those calls occurred, including `resources/read board://summary`, `tools/call create_issue`, and two `resources/read issue://1` entries, but a small scripted MCP client would have made verification output clearer than long shell-escaped curl payloads.

There were two minor environment/tooling papercuts: npm warned that `esbuild@0.28.2` had `install scripts not yet covered by allowScripts`, though execution still worked, and the final attempt to inspect changes failed with `fatal: not a git repository (or any of the parent directories): .git`. Despite those detours, typechecking succeeded immediately after implementation with `npx tsc --noEmit` returning no errors.
