The main friction was API and protocol discovery. The agent first tried npm metadata/README, but `npm view mcp-use readme --json` produced `SyntaxError: /tmp/mcp-use-readme.json: Unexpected end of JSON input`, and the fallback `npm view mcp-use readme` returned an empty output. It then relied heavily on installed declarations and implementation searches, including `sed -n '1,300p' node_modules/mcp-use/dist/server.d.ts` and `rg -n "createServer|tool\\(|streamable|listen\\(" node_modules/mcp-use/dist`, which revealed the useful listener contract: `listen(port?: number | undefined, options?: ListenOptions)`.

Verification took the wrong protocol path initially. A hand-written curl request mixed an `initialize` body with `MCP-Protocol-Version: 2026-07-28`, yielding the fairly specific but surprising error: `the request headers and body disagree: an initialize request (legacy handshake) was sent with a modern MCP-Protocol-Version header`. The agent then searched the bundled client declarations—`rg -n "Streamable|class Client|callTool|connect\\(" node_modules/@modelcontextprotocol/client/dist/*.d.mts`—and switched to `Client` plus `StreamableHTTPClientTransport`, which worked.

The npm scaffold also caused a small verification papercut because `npm init -y` created `"type": "commonjs"`. Consequently, the first `tsx --eval` client used top-level await and failed three times with `Top-level await is currently not supported with the "cjs" output format`; wrapping the code in `void (async () => { ... })();` resolved it and returned `{"content":[{"type":"text","text":"42"}]}`. Despite these detours, the implementation itself typechecked immediately: the first `npx tsc --noEmit` had `exitCode":0`.
