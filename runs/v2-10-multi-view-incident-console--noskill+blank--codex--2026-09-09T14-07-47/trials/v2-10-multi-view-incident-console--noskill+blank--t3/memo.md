The decisive wrong turn was entry-file placement: the agent followed package guidance saying `Replace its index.ts` and created root `index.ts`, while the grader required `src/server.ts` or `src/index.ts` (`entry: FAIL — no entry file found (tried: src/server.ts, src/index.ts)`). This was especially misleading because the SDK workflow accepted that layout: `[mcp-use] built index.ts + views ... → .mcp-use/build/index.js`, so local build/start verification did not expose the contract mismatch.

The agent spent substantial discovery effort inspecting npm artifacts rather than using a skill file: it ran `npm pack mcp-use@2.0.4`, searched the extracted README with `rg -n -i "view|app|registerTool|tool"`, and unpacked `create-mcp-use-app@2.0.6` to inspect `dist/templates/mcp-apps/index.ts`, `package.json`, and `tsconfig.json`. That template reinforced the root-entry choice because its archive contained `dist/templates/mcp-apps/index.ts`.

Protocol verification took an avoidable failed attempt: the first initialize request returned `400 Bad Request` because `an initialize request (legacy handshake) was sent with a modern MCP-Protocol-Version header`; retrying without that header and with `"protocolVersion":"2025-11-25"` succeeded.

The CLI dependency flow was also confusing. `mcp-use client connect` printed `[mcp-use] installing @mcp-use/client…` and `added 1 package`, but immediately failed with `@mcp-use/client is not installed`; `npm ls` then showed `@mcp-use/client@2.3.0`, and rerunning the same connect command worked. This also introduced a version-skew surprise: the project used `mcp-use@2.0.4`, while server logs identified the verification client as `mcp-use/2.3.0`.

Cleanup/verification had minor shell friction: appending `git status --short` made an otherwise successful final check exit 128 with `fatal: not a git repository`, and stopping the server required killing two PIDs after the first kill left `node node_modules/.bin/mcp-use start` running.
