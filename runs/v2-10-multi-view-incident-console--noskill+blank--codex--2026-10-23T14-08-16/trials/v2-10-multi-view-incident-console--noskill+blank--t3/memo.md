The decisive mistake was entry placement: the server was created as root-level `index.ts` (`[tool] fileChange({"event":"create","path":"index.ts"})`) rather than a conventional `src/index.ts` or `src/server.ts`. This was masked because the CLI auto-discovered and built it successfully: `[mcp-use] built index.ts + views ... → .mcp-use/build/index.js`, so the agent never noticed the grader-facing entry-path mismatch.

With no skill file available, the agent leaned heavily on installed-package inspection, including `sed -n '1,220p' node_modules/mcp-use/README.md`, searches for `"registerTool|registerApp|resource|view|ui://"`, and direct reads of `node_modules/mcp-use/dist/tools.d.ts` and `use-tool-context.d.ts`. It also used CLI help—`npx mcp-use build --help` and `npx mcp-use start --help`—but did not turn the visible `--entry <path>` option into a stable conventional source layout.

Dependency compatibility cost a retry: the first typecheck reported Zod schemas lacked `jsonSchema`—`Property 'jsonSchema' is missing`—after which the agent queried `npm view zod version`, modified `package.json`, and reinstalled. A second type error then exposed readonly output data—`structuredContent: { incidents: readonly [...]`—requiring another `index.ts` edit.

Verification also had avoidable false starts. `git diff --check` failed because `warning: Not a git repository`, interrupting a command chain after successful build/typecheck. The first Node verifier incorrectly parsed SSE and raised `tools/list failed: 200 event: message`; the next verifier searched generated HTML for literal source syntax and reported `"listHtmlMarker":false,"detailHtmlMarker":false`, even though inspection showed generated JSX as `{"data-view":\`incident-list\`}`. The final adjusted verifier did pass its checks, reporting `"exactTools": true`, both expected resource MIME types, and matching `"resultViews"`, but that runtime success reinforced the overlooked entry-location problem.
