The decisive wrong turn was choosing a root entry at `server.ts` rather than `src/server.ts` or `src/index.ts`. The agent explicitly concluded, “`server.ts` default-exports the server,” and the CLI reinforced this with “`built server.ts + views ... → .mcp-use/build/index.js`,” but the produced entry remained only `server.ts` (`export default server;`). This local CLI success masked the entry-layout incompatibility that blocked external evaluation.

The agent leaned heavily on installed-package inspection rather than a skill file or fetched docs: it ran `sed ... node_modules/mcp-use/README.md`, inspected `node_modules/mcp-use/dist/server.d.ts`, and grepped CLI internals with `rg -n "server\\.ts|index\\.ts|default.*server|PORT|inline"`. Despite that investigation, it never created either conventional `src/` entry.

Typed view context caused repeated friction. Three checks failed with `Property 'incident' does not exist on type 'never'`, `Property 'incidents' does not exist on type 'never'`, and an implicit-`any` error. Even after generating `mcp-env.d.ts`, the same errors persisted, leading the views to bypass SDK typing via `useToolContext() as unknown as` in both `views/incident-detail/view.tsx` and `views/incident-list/view.tsx`.
