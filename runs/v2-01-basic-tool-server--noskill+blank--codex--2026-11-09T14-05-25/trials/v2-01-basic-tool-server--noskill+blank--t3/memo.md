The agent had to discover the API locally rather than relying on prior guidance: it searched `node_modules/mcp-use` with `rg -n "streamable|HTTP|createMcpServer|MCPServer|tool\\("` and then inspected `node_modules/mcp-use/README.md`, `dist/server.d.ts`, `dist/tools.d.ts`, and `dist/config.d.ts`. The packaged README’s quickstart supplied the core pattern, including `import { MCPServer } from "mcp-use";`, `server.tool(`, Zod schemas, and structured tool results.

The main wrong turn was project configuration, not the SDK. The generated `package.json` ended up with both `"type": "module"` and a later `"type": "commonjs"`, causing the first typecheck to fail with `Cannot find name 'process'` and `The current file is a CommonJS module and cannot use 'await' at the top level.` Although `@types/node` had already been installed, TypeScript explicitly required adding Node types: `add 'node' to the types field in your tsconfig.` The agent then modified both `package.json` and `tsconfig.json`, after which typechecking passed.

HTTP verification required further protocol-shape discovery. A plain probe only returned `HTTP/1.1 204 No Content`, so the agent grepped bundled implementation files for `"initialize|tools/call|mcp-session-id|MCP-Protocol-Version"` before constructing a POST with `Accept: application/json, text/event-stream` and `MCP-Protocol-Version: 2025-11-25`. That call succeeded with `"text":"6.5"` and `"structuredContent":{"sum":6.5}`.

Process cleanup was mildly awkward: the background server command surfaced as `exitCode:143`, and the first cleanup attempt, `kill 488 && sleep 1 && ! ps -p 488,529,540`, itself returned `exitCode:1`. The agent consequently started and tested the server a second time, then killed it via process matching.
