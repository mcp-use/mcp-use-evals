The decisive wrong turn was placing the server at root `index.ts`; the produced source is `index.ts`, while the deterministic result says `entry: FAIL — no entry file found (tried: src/server.ts, src/index.ts)`. This mismatch was masked because the SDK CLI accepted the root entry: `"[mcp-use] built index.ts + views (incident-detail, incident-list) → .mcp-use/build/index.js"`, and the agent therefore concluded, `"The production build succeeded and the server is listening at /mcp"`.

The agent leaned heavily on npm package discovery rather than a supplied skill: it fetched `"npm view mcp-use@2.0.4 readme --json"` and inspected the newer scaffold with `"npm pack create-mcp-use-app@2.0.6"`. That scaffold explicitly contained `"dist/templates/mcp-apps/index.ts"` and a tsconfig including `"index.ts"`, likely reinforcing the root-entry choice even though the grader searched only `src/server.ts` and `src/index.ts`. The version mismatch between the inspected scaffold (`"create-mcp-use-app-2.0.6.tgz"`) and requested SDK (`"mcp-use@2.0.4"`) was an avoidable compatibility risk.

Verification was otherwise extensive but validated only the CLI’s interpretation: live calls showed `"ui/resourceUri":"ui://views/incident-list.html"` and `"ui/resourceUri":"ui://views/incident-detail.html"`, and resources reported `"mimeType":"text/html;profile=mcp-app"`. Because no check reproduced the grader’s entry-file discovery, substantial protocol verification did not catch the packaging-layout failure.

A minor papercut occurred when the agent assumed Git metadata existed: `"fatal: not a git repository (or any of the parent directories): .git"`. It recovered by rerunning without `git status`, but this was an unnecessary failed command.
