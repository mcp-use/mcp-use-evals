The main discovery friction was documentation access: the npm README fetch produced an empty file and failed with `SyntaxError: /tmp/mcp-use-readme.json: Unexpected end of JSON input`, followed by `0 /tmp/mcp-use-readme.json`. The agent then relied heavily on installed package internals, inspecting `node_modules/mcp-use/README.md`, `dist/server.d.ts`, `dist/resources.d.ts`, and grepping for `"resource\\(|streamable|listen\\("`; the declaration clarified port behavior with `Port precedence is the argument, PORT, config.port, then 3000`.

TypeScript configuration caused a small avoidable detour: the first typecheck failed with `Cannot find name 'process'` even though `@types/node@26.6.6` was installed, requiring a `tsconfig.json` modification. There was also an entrypoint/API-execution surprise under tsx: the agent explicitly reported, `the entrypoint’s direct-run guard did not behave correctly under tsx`, and replaced it with unconditional startup.

Process management consumed additional time. The first combined typecheck/start command apparently left the server running, so the next launch failed with `Error: listen EADDRINUSE: address already in use 127.0.0.1:3100`. Killing the npm parent was insufficient—the follow-up still showed `node node_modules/.bin/tsx src/server.ts`—so the agent had to kill child PIDs separately. Successful lifecycle scripts were also reported by the shell tool as failures because termination yielded `exitCode":143`, despite output confirming all state transitions and not-found checks. This made verification noisier than necessary and prompted a second full lifecycle run.
