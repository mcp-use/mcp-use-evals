The main friction was API discovery: the agent first queried npm with `npm view mcp-use version description repository.url dist.tarball --json && npm view mcp-use readme --json`, but the result exposed package metadata without useful README content. It then relied heavily on installed declarations, using `rg -n "class MCPServer|resource\(|httpStream|streamable|start\(" node_modules/mcp-use` and inspecting `node_modules/mcp-use/dist/server.d.ts`, `config.d.ts`, `resources.d.ts`, and `tools.d.ts` before implementing. This suggests the SDK’s resource-template and HTTP-listener shapes were not immediately discoverable from package-level documentation.

Dependency setup had minor churn: the agent initially ran `npm install mcp-use@2.10.1 zod@3.24.2`, later checked `npm view zod version` and got `4.6.7`, then a subsequent `npm install` reported `removed 4 packages, changed 1 package`. Nothing broke, but this was avoidable package-version investigation.

Verification required hand-written JSON-RPC curl requests such as `curl ... --data '{"jsonrpc":"2.0","id":1,"method":"initialize"...}'`, followed by separate calls for `resources/list`, `resources/read`, `tools/list`, `tools/call`, and `resources/templates/list`. The distinction between static resources and templates required an extra check: `resources/list` returned only `docs://index`, while `resources/templates/list` separately returned `"uriTemplate":"docs://{slug}"`.

The final server shutdown was reported as a failed tool result despite successful checks: `[result] {"exitCode":130,...,"status":"failed"}` followed logs showing all requests returned `200`. This appears to be process-management noise from stopping the long-running server rather than an implementation problem.
