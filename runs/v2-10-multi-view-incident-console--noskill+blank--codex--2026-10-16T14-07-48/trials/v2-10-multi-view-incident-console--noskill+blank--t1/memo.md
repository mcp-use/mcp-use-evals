The decisive wrong turn was entry-file placement: the agent followed the package README’s root-level guidance, `Replace its index.ts`, and created `index.ts`, while the grader expected `src/server.ts` or `src/index.ts` (`entry: FAIL — no entry file found (tried: src/server.ts, src/index.ts)`). This is especially misleading because the SDK CLI accepted that layout and reported `[mcp-use] built index.ts + views ... → .mcp-use/build/index.js`, so local verification did not expose the contract mismatch.

The agent spent substantial discovery effort grepping installed SDK files—`rg -n "registerTool|registerApp|ui://|mcp-app|McpServer|default" node_modules/mcp-use`—and reading `node_modules/mcp-use/README.md`, declaration files, CLI help, and package metadata. It also searched for entry resolution with `rg -n "resolveEntry|server\\.ts|index\\.ts|entry.*candidates"`, but still selected the root README example rather than the grader-compatible `src/` convention.

View typing caused two repair cycles. Initial typechecking reported `Property 'incident' does not exist on type '{}'`, `Property 'incidents' does not exist on type '{}'`, and `Type '{}' is not assignable to type 'ReactNode'`; the produced views ultimately use assertions such as `views/incident-detail/view.tsx: const incident = (toolOutput as { incident?: Incident } | undefined)?.incident`, suggesting the generated `useToolContext` typing was not immediately useful.

Protocol verification also hit an optional-dependency surprise: `mcp-use client` failed with `@mcp-use/client is required for this command`, requiring an extra `npm install -D @mcp-use/client@2.0.0`. Final marker checking needed a retry after the first regex command exited with no output, and the cleanup command produced unrelated noise because `git diff --check` returned `warning: Not a git repository.`
