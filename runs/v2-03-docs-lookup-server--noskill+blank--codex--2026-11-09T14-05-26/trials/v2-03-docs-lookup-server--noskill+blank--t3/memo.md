The main friction was SDK/API discovery: the agent first queried npm metadata with `npm view mcp-use readme --json`, then inspected installed declarations via `rg -n "resource\\(|listen|streamable|MCPServer"` and `sed` on `node_modules/mcp-use/dist/resources.d.ts`, `server.d.ts`, and `tools.d.ts`. No skill file or external docs URL was used; the run leaned primarily on package README/type declarations.

The initial scaffold introduced contradictory module settings: `package.json` contained both `"type": "module"` and `"type": "commonjs"`. This caused the first typecheck to fail with `The 'import.meta' meta-property is not allowed in files which will build into CommonJS output` and `The current file is a CommonJS module and cannot use 'await' at the top level`, requiring package and tsconfig edits.

A verification command also mixed a valid typecheck with an inapplicable repository check: `npx tsc --noEmit && git diff --check && git status --short`. It exited 129 because `Not a git repository`, obscuring that the typecheck itself had succeeded.

The SDK’s bundled CLI looked promising for verification—`mcp-use client --help` advertised `Connect to and invoke saved HTTP(S) MCP servers`—but invocation failed first with `Unknown saved server: documentation-test`, then connection failed because `@mcp-use/client is required for this command.` The agent consequently fell back to numerous hand-written `curl` JSON-RPC requests for initialization, resource reads, template listing, and tool calls.

Optional telemetry created cleanup work and an API-loading surprise. Running the server produced `./.mcp-use/usage.json`; the agent deleted it, grepped bundled JavaScript for `MCP_USE_ANONYMIZED_TELEMETRY`, and changed the source to set `process.env.MCP_USE_ANONYMIZED_TELEMETRY = "false"` before dynamically importing the SDK: `const [{ MCPServer }, { z }] = await Promise.all([import("mcp-use"), import("zod")]);`. This required an extra server restart and verification pass.
