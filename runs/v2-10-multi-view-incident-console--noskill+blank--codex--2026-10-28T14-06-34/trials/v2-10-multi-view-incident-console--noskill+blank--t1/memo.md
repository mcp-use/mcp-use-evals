The decisive wrong turn was placing the server at repository-root `index.ts`; the agent followed the SDK README’s instruction, `Replace its index.ts`, and the CLI reinforced that choice with `[mcp-use] built index.ts + views`, but the grading workflow required `src/server.ts` or `src/index.ts` and reported `entry: FAIL — no entry file found (tried: src/server.ts, src/index.ts)`. The agent never created either expected path; its final file inventory showed only `./index.ts`.

Discovery relied heavily on installed-package inspection rather than a skill file: the agent ran `find node_modules/mcp-use`, searched declarations with `rg -n "registerTool|registerApp|registerResource|ui://"`, and read `node_modules/mcp-use/README.md`, `dist/index.d.ts`, `dist/tools.d.ts`, and React hook declarations. That investigation produced working SDK usage, but it did not reveal the external entry-path convention.

The first production start exposed an ESM scaffold papercut: `Cannot use import statement outside a module` accompanied by `Make sure to set "type": "module" in the nearest package.json file`. After modifying `package.json`, a subsequent start was actually left running, making the next attempt fail with `listen EADDRINUSE: address already in use 127.0.0.1:3100`; the process listing confirmed `node node_modules/.bin/mcp-use start`.

Verification also lost time to optional-client behavior and version drift. Running `npx mcp-use client` said `[mcp-use] installing @mcp-use/client…` but then immediately reported `@mcp-use/client is not installed`; a manual `npm install @mcp-use/client@2.0.4` stalled while the installed dependency became `^2.4.5`, and npm warned about `Found: @mcp-use/client@2.4.5`. The agent nevertheless completed extensive protocol verification—`tools list`, `resources list/read`, and tool calls—but that success masked the packaging mismatch later caught by the deterministic entry check.
