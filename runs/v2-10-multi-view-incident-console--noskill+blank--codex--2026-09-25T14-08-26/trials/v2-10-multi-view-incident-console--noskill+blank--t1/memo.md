The decisive wrong turn was entry-file placement: the agent followed the package README’s root-entry example, quoted as `Replace its index.ts with a view-bound tool like this`, and created `index.ts`, while the grader required `src/server.ts` or `src/index.ts` and reported `entry: FAIL — no entry file found (tried: src/server.ts, src/index.ts)`. This is a notable convention mismatch because the SDK itself successfully accepted the root file: `[mcp-use] built index.ts + views (incident-detail, incident-list) → .mcp-use/build/index.js`.

The agent leaned heavily on installed-package discovery rather than a skill file or fetched docs: it searched `node_modules/mcp-use` with `rg -n "registerTool|registerApp|McpServer|App"` and inspected `node_modules/mcp-use/README.md`, `dist/server.d.ts`, `dist/tools.d.ts`, and `dist/views/register.d.ts`. It also consulted CLI help via `npx mcp-use --help`, `npx mcp-use build --help`, and `npx mcp-use start --help`.

Typed view context caused one repair cycle. The first typecheck produced `Property 'incident' does not exist on type 'never'`, `Property 'incidents' does not exist on type 'never'`, and `Parameter 'incident' implicitly has an 'any' type`; the agent then modified both view files before `npx tsc --noEmit` succeeded.

Verification also consumed avoidable retries. The first custom SSE parser failed with `No JSON-RPC response for tools/list` despite the body containing `event: message` and `data: {...}`. After changing parsing, an assertion expected literal HTML quoting and failed with `Error: missing data-view=\"incident-list\"`; inspection showed the inline bundle emitted ``"data-view":`incident-list` `` instead. A final unrelated check combined successful commands with `git status --short` and therefore exited on `fatal: not a git repository`, obscuring that the server had answered `GET /mcp 204 in 2ms`.
