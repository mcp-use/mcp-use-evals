The decisive integration miss was entry placement: the agent created root-level `index.ts` (`[tool] fileChange({"event":"create","path":"index.ts"})`), while the grader searched `src/server.ts` and `src/index.ts`; the final file listing likewise showed only `index.ts` and no `src/`: `rg --files ...` → `index.ts ... views/incident-list/view.tsx`. This was easy to overlook because the SDK CLI accepted that layout and reported success: `[mcp-use] built index.ts + views ... → .mcp-use/build/index.js`.

The agent leaned heavily on installed-package discovery rather than a skill or fetched docs: it read `node_modules/mcp-use/README.md`, inspected declarations such as `node_modules/mcp-use/dist/server.d.ts`, and grepped implementation files with `rg -n "entry|viewsDir|view.tsx|mcp-app..." node_modules/...`. That investigation established SDK behavior, but it did not reconcile the project layout with the expected conventional entry path.

There was avoidable package configuration churn. The first production start failed with `Cannot use import statement outside a module`; inspection then revealed duplicate contradictory keys in `package.json`: `"type": "module"` followed later by `"type": "commonjs"`. After modifying the package, a combined build/typecheck/start command left a server running, and the next explicit start failed with `listen EADDRINUSE: address already in use 127.0.0.1:3100`.

Verification also hit SDK/tooling papercuts. `npx mcp-use client` said it was `installing @mcp-use/client…`, then immediately failed with `@mcp-use/client is not installed`, although the next `npm ls @mcp-use/client` showed it present. Piping resource output through `rg -m 1` triggered an unhandled `Error: write EPIPE`, and cleanup diagnostics encountered `/bin/bash: line 1: fuser: command not found`. Despite these detours, endpoint-level checks did work, including `tools/call list_incidents`, `tools/call get_incident`, and both `resources/read ui://views/...` calls.
