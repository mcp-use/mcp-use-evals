The decisive wrong turn was placing the entry at root as `index.ts`; the SDK README explicitly said `Replace its \`index.ts\``, and the agent’s node_modules grep found candidates including `index.ts`, but the deterministic contract reported `no entry file found (tried: src/server.ts, src/index.ts)`. Thus the SDK CLI accepted and built it — `[mcp-use] built index.ts + views ...` — while the grader could not discover it.

The agent relied heavily on installed-package discovery rather than a skill file: it searched `node_modules/mcp-use/README.md` and declarations with `rg -n "app|view|registerTool|tool\("`, then inspected CLI internals showing `var i=["src/index.ts",...,"index.ts",...]`. One discovery command also assumed a nonexistent layout and failed with `ls: cannot access 'node_modules/mcp-use/dist/cli': No such file or directory`.

Typed view registration caused a build/typecheck ordering papercut. Although build generated `[mcp-use] created mcp-env.d.ts`, the first typecheck produced `Property 'incident' does not exist on type 'unknown'` and `'view.toolOutput' is of type 'unknown'`; the agent then modified `tsconfig.json`, after which `npx tsc --noEmit` passed.

Manual modern-protocol verification consumed several retries because required envelope and header conventions were not initially known. The server successively rejected requests for `legacy handshake`, missing `_meta`, missing `io.modelcontextprotocol/protocolVersion`, missing `Mcp-Method`, and later missing `Mcp-Name`. Verification eventually succeeded with `PASS tools`, `PASS resources`, `PASS mime`, and `PASS resultViews`, but none of that exposed the grader’s stricter `src/` entry convention.
