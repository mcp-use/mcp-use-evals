The decisive wrong turn was entry placement: the agent created root-level `index.ts` (`[tool] fileChange({"event":"create","path":"index.ts"})`), while the grader searched `src/server.ts` and `src/index.ts`, producing `entry: FAIL — no entry file found`. This was especially misleading because the SDK CLI accepted that layout and reported `[mcp-use] built index.ts + views ... → .mcp-use/build/index.js`, so the agent’s own build/start verification did not expose the contract mismatch.

With no skill scaffold available, the agent leaned heavily on installed-package discovery: it inspected `node_modules/mcp-use/dist/index.d.ts`, `views/index.d.ts`, `tools.d.ts`, and `server.d.ts`; searched API shape with `rg -n "bootstrapView|views/.*tsx|ViewModule|mcp-env|export default"`; and consulted `node_modules/mcp-use/README.md`, finding `Create views/weather-card/view.tsx`. It also explicitly investigated entry conventions using `rg -n "server\\.ts|index\\.ts|resolve.*entry|DEFAULT.*ENTRY|entryCandidates"`, but that search produced no useful entry guidance beyond an enormous bundled `index.js` match.

Verification had two avoidable detours. First, `npx mcp-use client connect ...` said `[mcp-use] installing @mcp-use/client…` but then failed with `@mcp-use/client is not installed`, even after npm reported `added 2 packages`; the agent then switched to raw `curl`. Second, its initial handshake mixed a modern header with a legacy initialize body and received `the request headers and body disagree`; it had to grep protocol dates from `node_modules/@modelcontextprotocol/core/dist` and retry with `2025-11-25`.

The final confidence statement, `The production build passed and is serving at /mcp`, was true for the CLI-selected root entry but masked the grader-facing entry convention. The source itself did default-export the server at `index.ts: export default server;`; the papercut was discoverability and project layout, not the server export API.
