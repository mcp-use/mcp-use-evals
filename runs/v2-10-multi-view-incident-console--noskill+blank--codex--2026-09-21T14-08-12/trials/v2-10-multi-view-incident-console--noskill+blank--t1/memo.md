The decisive wrong turn was placing the entry at repository root as `index.ts`; the produced declaration also points there (`mcp-env.d.ts`: `tools: typeof import("./index.js");`), while the deterministic workflow searched only `src/server.ts` and `src/index.ts`. The agent relied on the CLI accepting this layout—`[mcp-use] built index.ts + views ... → .mcp-use/build/index.js`—and consequently reported success as `Default server export in .../index.ts`, without checking the expected conventional entry path.

Discovery depended heavily on installed-package inspection rather than a skill or external docs: it ran `sed -n '1,240p' node_modules/mcp-use/README.md`, inspected `node_modules/mcp-use/dist/server.d.ts`, `tools.d.ts`, and `use-tool-context.d.ts`, and grepped with `rg -n "declare module.*mcp-use/react|Register|mcp-env" node_modules/mcp-use node_modules/@mcp-use`. The initial npm README lookup was unhelpful: `npm view mcp-use@2.0.4 readme --json` returned only npm upgrade notices.

There was a dependency-version papercut after rewriting the generated package metadata: `npm ls` failed with `@types/node@26.6.2 invalid: "^24.10.1"` and `typescript@7.0.2 invalid: "^5.9.3"`. The agent corrected `package.json`, then used `npm install --package-lock-only`, after which build and typecheck passed.

The agent did perform substantial runtime verification against its own successful build: the server logged `tools/list`, `resources/list`, both `resources/read` calls, and both tool calls, while output showed `"mimeType":"text/html;profile=mcp-app"` and distinct `"ui/resourceUri"` values. However, that verification did not expose the packaging mismatch because every command used the root entry implicitly; even the CLI help had advertised `--entry <path>` and `--mcp-dir <dir>`, but the agent never exercised a clean/default consumer expecting `src/index.ts` or `src/server.ts`.
