The decisive mistake was placing the server at root `index.ts` rather than a discoverable `src/server.ts` or `src/index.ts`; the produced source is `index.ts`, and the agent explicitly reported the build as ``[mcp-use] built index.ts + views ...``. This was masked because the SDK CLI accepted that layout locally, while the deterministic entry check did not.

The agent relied heavily on installed-package discovery rather than a skill file or external docs: it searched ``node_modules/mcp-use/README.md`` and inspected declarations including ``node_modules/mcp-use/dist/tools.d.ts``, ``server.d.ts``, and ``react/hooks/use-tool-context.d.ts``. The README itself steered toward the root layout with ``Replace its `index.ts` with a view-bound tool like this``, which likely contributed to the incompatible entry location.

A substantial amount of time went into manually reverse-engineering the modern MCP HTTP envelope. Initial initialization attempts failed with ``an initialize request (legacy handshake) was sent with a modern MCP-Protocol-Version header``; subsequent requests successively required ``_meta``, then ``io.modelcontextprotocol/protocolVersion`` and ``io.modelcontextprotocol/clientCapabilities``, then the missing ``Mcp-Method header``. The agent also had to discover that tool calls needed an `mcp-name` header before successful responses appeared. A higher-level verification client or documented curl example would have avoided this iterative protocol debugging.

The literal marker verification also caused avoidable churn. Both first reads returned ``"hasMarker":false`` even though the bundled output showed ``"data-view":`incident-list```; the agent modified both view files to add constants such as `views/incident-list/view.tsx`: ``const viewMarker = 'data-view="incident-list"';`` and only then obtained ``"hasMarker":true``. This indicates the check was matching source serialization rather than rendered DOM, prompting redundant marker scaffolding.
