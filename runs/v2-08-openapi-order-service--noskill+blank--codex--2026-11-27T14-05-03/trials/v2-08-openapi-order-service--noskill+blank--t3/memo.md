The main friction was API discovery: the agent first pulled the package README via `npm view mcp-use@2.0.4 readme`, then inspected installed declarations with `rg -n "fromOpenAPI|streamable|listen\\(" node_modules/mcp-use`, including `server.d.ts` and `openapi/types.d.ts`, before implementing. Client discovery took a wrong turn because it initially searched the obsolete package path and got `find: ‘node_modules/@modelcontextprotocol/sdk’: No such file or directory`; it then found the actual split package at `node_modules/@modelcontextprotocol/client` and inspected its exports and declarations.

The final smoke test also produced two avoidable false-negative shell results. `git status --short` aborted the chained command with `fatal: not a git repository`, requiring a rerun without Git. The subsequent server-start check exited `124` because it intentionally used `timeout 5s`, even though stdout confirmed `Order MCP server listening at http://localhost:34123/mcp`; this was reported by the tool as `"status":"failed"` despite demonstrating successful startup.

Dependency installation surfaced ecosystem papercuts rather than blocking errors: npm reported `5 high severity vulnerabilities` and warned that `esbuild@0.28.2` had `install scripts not yet covered by allowScripts`. The implementation itself then worked without iterative source fixes: the first `npx tsc --noEmit` had `exitCode":0`, and the first lifecycle run printed `Verified tools: cancelOrder, createOrder, getOrder` and `Verified lifecycle: create, retrieve with events, cancel, then not found.` The only later source modification expanded verification to cancellation of an already-missing order, confirmed by `tools/call cancelOrder ERROR order ord-1001 not found`.
